02

Le sujet

Une usine qui assemble des drones à la demande

Le programme lit des instructions en console et répond sans jamais planter. Il raisonne sur un stock de pièces et sur la façon d'assembler chaque drone.

  • STOCKS / NEEDED_STOCKS — inventaire disponible et nécessaire
  • INSTRUCTIONS — la séquence d'assemblage détaillée
  • VERIFY / PRODUCE — vérifier puis produire une commande
  • ADD_TEMPLATE — enregistrer un nouveau modèle de drone

Un drone = 6 éléments

coque
1 — étanche (S) ou non
module principal
1 — reçoit un système
générateur(s)
1 à 2
déplacement
1 à 3 modules
contrôle
1 module
système
installé sur le module principal

3 phases imposées : implémentation naïve → design patterns → modules libres.

03

La démarche

Chaque pattern répond à une douleur réelle du code naïf

La version naïve compile et fonctionne — c'est un proof of concept volontairement « sale ». On introduit ensuite un pattern uniquement là où le code fait mal, pas par principe.

Phase 1 — Naïf

Tout en dur, un gros switch, données figées, génération d'instructions codée en dur.

Phase 2 — Patterns

Refactoring : modèle de domaine, catégorisation, dispatch des commandes, génération d'assemblage.

Phase 3 — Modules

Traçabilité, modifications de drones, commandes clients — chacun sert un nouveau pattern.

gros switch
→ Command : une classe par instruction
catégories en if/else
→ Strategy : une classe par catégorie
assemblage codé en dur
→ Builder : construction pas-à-pas
« qui a touché le stock ? »
→ Observer : le stock est écouté
drones sur-mesure
→ Decorator : modifications composables

05

Pattern 01 · Strategy

Catégoriser les drones

Le problème

4 catégories (Aérien, Marin, Terrestre, Submersible), chacune avec ses règles sur les types de pièces. Un drone doit appartenir à au moins une catégorie.

La solution

Chaque catégorie est une stratégie interchangeable : bool Matches(IDroneModel). Le service applique la liste.

Pourquoi ici

Ajouter une catégorie = ajouter une classe, sans toucher au reste (Open/Closed). Idéal quand des règles similaires se multiplient.

// une stratégie par catégorie
public sealed class AerialCategory : IDroneCategory
{
    public bool Matches(IDroneModel d)
        => d.Moves.Any(m => m.Is(PieceType.F))
        && d.System.Is(PieceType.D3);
}

// le contexte n'orchestre que l'abstraction
_categories.Any(c => c.Matches(drone));
06

Pattern 02 · Command

Chaque instruction, un objet

Le problème

Le code naïf : un switch géant dans la boucle principale. Chaque nouvelle instruction v3 l'alourdit.

La solution

Une interface IInstruction.Execute(args), une classe par commande, un dispatcher mot-clé → commande.

Pourquoi ici

Les 11 instructions deviennent isolées et testables. Le REPL ne connaît plus aucune commande : il délègue.

public interface IInstruction
{
    void Execute(string args);
}

// dispatcher (invoker)
if (_instructions.TryGetValue(keyword, out var cmd))
    cmd.Execute(args);
else
    Console.WriteLine($"ERROR `{keyword}` is not a recognized instruction");

Le REPL entier tient en ~10 lignes ; ajouter une instruction = 1 classe + 1 enregistrement.

07

Pattern 03 · Builder

Générer la séquence d'assemblage

Le problème

L'ordre d'assemblage a des contraintes (générateur avant le module principal, déplacement après la coque…) et il faut gérer 1 à 3 déplacements et 1 à 2 générateurs (v3).

La solution

Un directeur (DroneAssembler) encode l'ordre ; un builder produit la représentation console. On pourrait brancher un autre builder (graphe, JSON) sans toucher au directeur.

// le directeur encode l'ORDRE, pas la sortie
builder.BeginFrom(drone.Hull.Name);
foreach (var g in drone.Generators)
    builder.AssembleWith(g.Name);
foreach (var m in drone.Moves)
    builder.AssembleWith(m.Name);
builder.AssembleWith($"{Core}{{{System}}}");
builder.AssembleWith(drone.Processor.Name);

Choix assumé : chaque assemblage intermédiaire est nommé TMPk — toujours valide et généralisable à N pièces.

Pattern 04 · Observer

Tracer les mouvements de stock

Le problème

Le module GET_MOVEMENTS (5.2.3) exige l'historique de tout ce qui a bougé le stock — sans que le stock connaisse le journal.

La solution

Le StockService devient un sujet observable ; le MovementLog s'y abonne. Chaque entrée/sortie réelle notifie un mouvement. Le seeding initial reste silencieux.

Pourquoi ici

Découplage total : demain, une alerte « stock bas » s'abonne sans modifier le stock.

public void Remove(string name, int qty, string reason)
{
    _quantities[name] = Get(name) - qty;
    Notify(name, -qty, reason);   // -> observateurs
}

// abonnement (Factory)
Stock.Subscribe(Movements);
09

Pattern 05 · Decorator

Modifier un drone à la volée

Le problème

Les ARGS v3 (5.2.1) permettent WITH / WITHOUT / REPLACE — et ces clauses se composent sur un même drone.

La solution

Chaque modification enveloppe un IDroneModel et en présente une version transformée, avec la même interface. On empile les décorateurs.

Pourquoi ici

Composition naturelle et récursive ; le drone décoré reste consommable par toutes les instructions existantes.

// on empile les modifications
IDroneModel model = template;
model = new ReplacePiecesModification(model, repl);
model = new AddPiecesModification(model, adds);
model = new RemovePiecesModification(model, rem);

// le résultat est validé comme un vrai drone
DroneValidator.Validate(model, categories, out error);
10

Phase 3 · Modules

Quatre modules, chacun servant un pattern

Traçabilité — RECEIVE, GET_MOVEMENTS→Observer
Modification de drones — WITH/WITHOUT/REPLACE→Decorator
Commandes clients — ORDER / SEND / LIST_ORDER→Command + état
Contraintes de construction (5.1.2)→Builder + validation

≥ 2 déplacements

impose exactement 2 générateurs — sinon le template est rejeté.

Séparateur ;

dès qu'une modification est présente, les drones sont séparés par ; — le format initial reste accepté.

Cycle de commande

ORDER rend un id, SEND décrémente le reste, puis COMPLETED.

11

Regard critique

Patterns considérés puis écartés

Le sujet valorise autant les choix retenus que ceux abandonnés.

écarté Composite (arbre d'assemblage)

La notation [TMP2, Core{Sys}] est un arbre… mais en nommant chaque intermédiaire TMPk, le Builder suffit. Composite aurait été de la structure non utilisée en sortie.

écarté Singleton (stock global)

Tentant pour l'unicité du stock, mais nuit à la testabilité et masque les dépendances. Le stock est injecté par la Factory.

écarté Interpreter (grammaire ARGS)

La grammaire WITH/WITHOUT/REPLACE est un mini-langage. Un vrai Interpreter serait sur-dimensionné : un parseur descendant à la main reste plus lisible.

retenu léger Registry / Factory

Le TemplateRegistry et le catalogue de pièces jouent un rôle de fabrique/registre — assumé sans en faire un Abstract Factory formel.

12

Décisions & hypothèses

Là où le sujet laissait le choix

Catégorisation

Les règles de type ne contraignent que coque / générateur / déplacement + système. Module principal et de contrôle sont non limitants (texte du sujet). Vérifié : les 4 drones connus tombent chacun dans leur catégorie.

Compatibilité

Sujet vague → règle explicite : le core doit couvrir les dimensions (2D/3D) du système ; le processeur partage ≥ 1 dimension avec le système. Documenté dans Compatibility.cs.

Validation d'un drone modifié

Validation complète (construction + compatibilité + catégorie), pas seulement les contraintes de construction : un drone modifié reste un vrai drone.

Conventions de sortie

Stock initial 5/pièce, 0/drone ; TEMPLATE_ADDED, STOCK_UPDATED, ORDER-n ; système via la notation Core{System}.

14

Bilan

Ce que les patterns nous ont apporté

  • Extensibilité — ajouter catégorie, instruction ou modification = ajouter une classe.
  • Découplage — le stock ignore qui l'observe ; le REPL ignore les commandes.
  • Lisibilité — chaque fichier a une responsabilité unique.
  • Historique git — un commit par étape, patterns introduits progressivement.
